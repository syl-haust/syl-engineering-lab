# 课题①：双 Token 认证

## 1. 问题从哪来

常见的做法是登录后签发一个 JWT，之后每个请求带 `Authorization`，拦截器验签放行。
（我最初的项目也是这么做的 —— 直到发现它的有效期怎么设都不对。）

这个方案有一个绕不过去的矛盾：**有效期设多长都不对。**

| 有效期 | 后果 |
|---|---|
| 2 小时 | 用户用得正顺手突然掉线，体验差 |
| 30 天 | token 一旦泄露（日志、代理、XSS、手机丢失），攻击者能用 30 天 |
| 中间值 | 两个问题同时存在，只是都小一点 |

根因是 **JWT 是无状态凭证，服务端没法"撤回"一个已经签发出去的 token**。
要撤回，就必须引入状态；引入状态，就回到了 session 的老路。

双 Token 是这两条路的折中：**用一个短命的"通行证" + 一个长命的"换证凭证"**。

## 2. 设计

```
┌──────────┐   ① 登录     ┌──────────┐
│  客户端   │ ───────────▶ │  服务端   │
│          │ ◀─────────── │          │
│          │  access(15m) │          │
│          │  refresh(7d) │          │
└────┬─────┘              └──────────┘
     │
     │ ② 正常请求：只带 access
     │ ③ access 过期 → 401
     │ ④ 带 refresh 去换新的一对
     ▼
  refresh 一旦被使用，立刻失效（轮换）
```

**两个 token 的分工：**

- **access token**：高频使用，所以必须无状态、不查库。有效期压到 15 分钟，
  即便泄露，攻击窗口也很短。
- **refresh token**：低频使用，可以承受一次 Redis 查询。有效期 7 天，
  它是"能不能继续待在系统里"的凭证，所以必须可吊销。

---

## 3. 三个关键设计点

### 3.1 白名单而不是黑名单

存"哪些 token 有效"（白名单），而不是"哪些 token 已被吊销"（黑名单）。

- 白名单：只存活的 token，TTL 到期自动清理，容量 = 在线用户数。
- 黑名单：所有被吊销的 token 都要留着直到自然过期，只增不减。

**代价**：每个 access 请求多一次 Redis 查询（约 0.1ms）。
如果对性能敏感，可以去掉 access 白名单，代价是踢人最多延迟 15 分钟生效。

### 3.2 refresh 轮换（rotation）

刷新时**不是延长旧的**，而是删掉旧的、签发全新的一对。

为什么？假设 refresh token 被截获但没有被轮换：
攻击者可以在 7 天内反复续期，用户完全无感。
轮换之后，攻击者一旦使用，真实用户下次刷新就会失败 ——
等于免费获得一个失窃告警。

### 3.3 并发刷新防重放 —— 这个方案最容易踩的坑

**现象**：用户打开 5 个标签页，同时有 3 个标签页的 access token 过期，
前端同时发起 3 个刷新请求，带的是**同一个** refresh token。

如果刷新逻辑是"删旧 + 发新"，那么：
- 第 1 个请求成功，删掉旧 token，签发新 token A
- 第 2 个请求发现 token 已不存在 → 判定为非法 → **用户被踢下线**

用户什么都没做错，却被登出了。

**解法**：把"删除"当作分布式锁。Redis 的 `DEL` 是单线程原子操作，
返回 1 的那个请求拿到刷新资格，返回 0 的说明别人刚刷过。

```java
public boolean rotate(String oldJti) {
    Boolean deleted = redis.delete(key(oldJti));   // 原子
    return Boolean.TRUE.equals(deleted);
}
```

并发时第 2、3 个请求收到 `409 REFRESH_REJECTED`。
**前端约定**：收到 409 不是跳登录页，而是使用本地已经拿到的新 token 重试。

几个细节：
- 不用 `Redisson` 分布式锁：`DEL` 本身就是原子的，加锁反而多一次 RTT。
- 不用"查询再删除"两步：查和删之间有窗口，并发下两个都能查到。
- 为什么不是直接返回新 token 给所有并发请求：那样同一个 refresh token 会签发多对，
  token 数量失控，也无法判断哪个是"真正的"当前会话。

## 4. 时序：一次完整的并发刷新

```
t0   3 个请求同时带 refreshToken(JTI_old) 到达
t1   请求1: DEL lab:auth:refresh:JTI_old → 1  ✅ 获得资格
t2   请求2: DEL lab:auth:refresh:JTI_old → 0  ❌ 409
t3   请求3: DEL lab:auth:refresh:JTI_old → 0  ❌ 409
t4   请求1 签发 access(JTI_new) + refresh(JTI_new)，写 Redis
t5   前端收到 409 的请求用请求1 返回的新 access 继续
```

---

## 5. 代价与取舍

| 取舍 | 说明 |
|---|---|
| 多一次 Redis 查询 | access 白名单校验。可关闭，代价是踢人延迟 15 分钟 |
| 需要 Redis 高可用 | refresh 存 Redis，Redis 挂了刷新功能不可用（access 仍有效 15 分钟，是缓冲） |
| 前端复杂度上升 | 要处理 401→刷新→重试 的拦截逻辑，以及 409 的复用逻辑 |
| 时钟偏差 | JWT 依赖服务端时钟，多实例需要 NTP 同步 |

## 6. 如果继续做，会怎么演进

1. **refresh token 绑定指纹**：把 UA + IP 段 hash 进 token，换证时校验，防 token 盗用。
2. **单设备单会话 / 多设备会话管理**：Redis 里按 `userId → Set<jti>` 维护，支持"踢掉其他设备"。
3. **滚动刷新**：在 access 剩余 1/3 有效期时主动续，减少一次 401 往返。
