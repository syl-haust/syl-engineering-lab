# 课题③：声明式接口幂等

## 1. 问题从哪来

常见的订单号生成是 `String.valueOf(System.currentTimeMillis())`，带来两个隐患：
毫秒级并发会撞号；更重要的是，**没有任何机制阻止同一笔业务被提交两次**。

重复提交的来源不止"用户连点"：

| 来源 | 说明 |
|---|---|
| 用户手抖连点 | 前端没做按钮防抖，或防抖失效 |
| 网关超时重试 | 请求其实成功了，但响应超时，客户端重试 |
| 移动端弱网 | 请求发出去，响应没回来，用户再点一次 |
| MQ 重复投递 | 至少一次语义，消费端也会重复执行 |
| 定时任务重跑 | 任务失败后人工重跑 |

**只在前端做防抖是不够的**：拦截器、网关、重试框架都会绕过前端。
幂等必须做在服务端，而且要做在**业务写入口**。

---

## 2. 三层防护

```
请求进入
   │
   ├─ 第1层：Idempotency-Key 请求头（业务层唯一标识）
   │         同一次用户操作的所有重试带同一个 key
   │
   ├─ 第2层：Redis Lua 三态占位（快速路径，挡住 99% 重复）
   │         PROCESSING / DONE
   │
   └─ 第3层：DB 唯一索引（兜底，Redis 挂了/过期了也不会重复）
```

为什么要三层？任何一层单独用都有洞：

| 只用 | 漏洞 |
|---|---|
| 只用 Redis | Redis 重启丢数据 / key 过期后重复请求穿透 |
| 只用 DB 唯一索引 | 每次请求都打到 DB，热点行压力大；且拿不到"处理中"语义 |
| 只用前端防抖 | 网关重试、MQ 重投完全绕过 |

---

## 3. 关键设计点

### 3.1 为什么不直接用 SETNX

`setIfAbsent` 只能区分"第一次"和"非第一次"，无法区分：

- **第一次还在处理中**（业务还没跑完）→ 应该告诉调用方"请稍后重试"
- **第一次已经处理完** → 应该直接回放那次的结果

如果把这两种情况都当成"重复"，用户重试拿到的就是失败，
或者拿到一个被吞掉的结果。这就是"幂等"最常见的实现错误。

解法是**三态**，用 Lua 一次原子读写完成：

```lua
local v = redis.call('get', KEYS[1])
if v == false then
  redis.call('set', KEYS[1], 'PROCESSING', 'EX', ttl)
  return 1                                  -- 首次，去执行业务
end
if v == 'DONE' then return 2 end            -- 已完成，回放结果
return 3                                     -- 处理中，请稍后重试
```

### 3.2 业务成功才置 DONE，失败要释放

业务抛异常时必须删掉占位，否则用户的所有重试都会得到 429，
这个请求就永远卡死了。

### 3.3 幂等键怎么设计

```java
key = prefix + ":" + userId + ":" + methodName + ":" + requestKey
```

- `userId`：不同用户的相同请求不能互相影响
- `methodName`：同一个 key 用在不同接口上不能串
- `requestKey`：前端/网关生成，**同一次操作的重试必须复用同一个值**

如果调用方没传 key，就退化成 `no-key`，此时只能挡住"同用户同方法"的连点，
粒度较粗，但也能覆盖大部分场景。

---

## 4. 幂等 vs 防重 vs 乐观锁

这三个概念经常被混为一谈：

| 概念 | 解决什么 | 典型手段 |
|---|---|---|
| **幂等** | 同一个请求重复执行，结果一致 | 唯一键、token 去重 |
| **防重** | 短时间内的重复点击 | 前端防抖、Redis 短期 key |
| **乐观锁** | 并发更新同一条记录时丢失更新 | `where version = ?` |

本课题实现的是**幂等**（含防重），乐观锁属于并发控制，不在范围内。
一个接口可能三者都需要，要按具体语义组合。

---

## 5. 代价与取舍

| 取舍 | 说明 |
|---|---|
| 要求调用方传 Idempotency-Key | 前端/网关要配合；不传时退化为粗粒度 |
| 结果缓存会占内存 | 只缓存成功结果，TTL 默认 5 分钟 |
| 返回值必须可序列化 | 用 JSON 存，DTO 要保持无副作用 |
| 不能覆盖"部分成功" | 如果业务里有远程调用且回滚不彻底，幂等只管"不重复执行"，不管"中途失败" |

## 6. 对应代码

| 文件 | 职责 |
|---|---|
| `idempotent/Idempotent.java` | 注解定义，`prefix` / `ttlSeconds` / `replayResult` |

| `idempotent/IdempotentRecordMapper.java` | DB 兜底层 |
| `idempotent/ResultCodec.java` | 返回值序列化回放 |

用法：

```java
@PostMapping("/submit")
@Idempotent(prefix = "order:submit", ttlSeconds = 300)
public Map<String, Object> submit(@RequestBody SubmitRequest req) { ... }
```
