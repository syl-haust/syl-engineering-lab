# 课题②：可靠异步下单（本地消息表 + RabbitMQ 延时队列）

## 1. 问题从哪来

典型的下单实现是同步串行的：

```
校验库存 → 写 order_info → 写 order_item → 写 order_log → 远程调购物车删除
```

三个问题：

1. **耗时叠加**：每一步都要等上一步返回，总耗时是各步之和。
2. **强耦合**：清购物车是"锦上添花"的动作，却能让整个下单失败。
   购物车服务抖一下，用户就下不了单。
3. **没有事务**：`order_info`、`order_item`、`order_log` 是三次独立写，
   中间异常会留下"有订单没明细"的脏数据。

再加上一个更本质的问题：**订单 30 分钟未支付要自动取消，原项目完全没有这个机制。**

---

## 2. 为什么不能用"定时任务扫表"做超时取消

最朴素的写法：

```sql
-- 每分钟跑一次
select * from order_info where status = 0 and create_time < now() - interval 30 minute
```

问题：

| 问题 | 说明 |
|---|---|
| 索引失效 | `create_time` 上没索引就是全表扫；建了索引，`status=0` 选择性又很低 |
| 和业务抢资源 | 扫表和用户查订单走同一个库，大促时雪上加霜 |
| 延迟不精确 | 每分钟扫一次，最坏情况下订单会晚 60 秒才取消 |
| 多实例重复执行 | 3 个应用实例同时扫，会重复处理（要加分布式锁） |

把"到点了该干活"变成一次**消息投递**，这些问题一次性解决。

---

## 3. 延时队列

```
下单 ──▶ lab.order.delay.exchange ──▶ lab.order.delay.30m.queue
                                          │  (x-message-ttl = 30min)
                                          │  消息到期
                                          ▼
                                    x-dead-letter-exchange
                                          │
                                          ▼
                              lab.order.expire.exchange ──▶ lab.order.expire.queue
                                                                    │
                                                                    ▼
                                                           取消未支付订单
```

### 一个必须知道的坑

**延时队列不能用「队列级 TTL」，要用「消息级 TTL」。**

队列级 TTL 是**队头阻塞**的：

```
投递顺序: [消息A TTL=30min] → [消息B TTL=5min]
结果:     消息B 必须等 A 出队后才能过期，实际延迟 30 分钟
```

这里有两条正确路线：

1. **每个延时档位一个队列**（本项目采用）：30 分钟一个队列、10 分钟一个队列……
   每个队列的 `x-message-ttl` 固定，不会出现不同 TTL 混排。
   缺点是档位是硬编码的。
2. **`rabbitmq-delayed-message-exchange` 插件**：消息级 TTL，任意延时，
   但需要安装插件，且管理台看不到"待投递"的消息。

本项目选 1，因为它零插件依赖，且演示效果最直观。

## 4. 保证消息不丢：本地消息表（Transactional Outbox）

这是本课题最有含金量的部分。**"写订单"和"发消息"无法放进同一个本地事务。**

三种朴素做法都不行：

| 做法 | 失败场景 |
|---|---|
| 先发 MQ 再写库 | 消息先到，消费端查订单查不到 → 空指针 / 误判取消 |
| 先写库再发 MQ | 写库成功后进程崩溃，消息永远发不出去 → 订单永远不会被取消 |
| 用 MQ 的事务机制 | RabbitMQ 的 tx 只保证"消息到 broker"，不覆盖业务库 |

**本地消息表的做法**（也是业界 Outbox 模式）：

```
事务开始
  ├── insert demo_order        (订单)
  └── insert local_message     (要发的消息，status=0)
事务提交
     │
     ├── 立即发一次 MQ（低延迟路径）→ confirm 成功则 status=1
     └── 失败 / 崩溃 → LocalMessageRelay 每 5 秒扫描 status=0 的记录补发（兜底路径）
```

关键点：**订单和消息记录在同一个本地事务里**，要么都成功要么都失败，
不会出现"有订单没消息"或"有消息没订单"。

### 退避重试

补发失败不能固定间隔重试，否则 broker 挂掉时会把连接打爆。
这里用指数退避：1s → 2s → 4s → 8s …… 上限 5 分钟。

```
retry_count: 0  1  2  3  4   5   6   7   8  ...  (capped)
delay(s)   : 1  2  4  8  16  32  64  128 256 ... 300
```

### 至少一次语义

本地消息表 + 重试 = **消息会被重复投递**（至少一次）。
所以消费端必须幂等 —— 见课题③的思路：`consumed_message` 表用 `messageId` 唯一索引，
插入成功才处理，冲突直接 ack。

## 5. RabbitMQ 可靠性链路全览

| 环节 | 风险 | 本项目做法 |
|---|---|---|
| 生产 → 交换机 | 消息没到 broker | `publisher-confirm-type: correlated`，回调 ack/nack |
| 交换机 → 队列 | 路由不到任何队列，静默丢弃 | `publisher-returns: true` + `mandatory: true`，returns 回调 |
| 队列 → 消费者 | 消费者宕机，消息丢失 | `acknowledge-mode: auto`（处理完才 ack）+ `default-requeue-rejected: true` |
| 消费失败 | 无限重投，死循环 | `spring.rabbitmq.listener.simple.retry` 最多 3 次 + 死信队列 |
| 重复消费 | 重复扣款、重复取消 | `consumed_message` 唯一索引幂等 |
| 业务与发消息一致性 | 订单有了消息没发 | 本地消息表 + 定时补偿 |

> **注意**：`publisher-confirm` 只保证"到交换机"，`publisher-return` 只覆盖"到交换机但没队列"。
> 两者必须同时开启，缺一个就有一类消息会静默丢失。

## 6. 代价与取舍

| 取舍 | 说明 |
|---|---|
| 消息会重复 | 至少一次语义，消费端必须幂等。不能省 |
| 多一张表 | local_message 会持续增长，需要定时清理（本项目 3 点清理 7 天前记录） |
| 最终一致 | 用户下单成功后，下游可能有几百毫秒延迟。对有强一致要求的场景不适用 |
| 多实例扫描 | 本项目用单实例定时器演示，生产环境要换成分布式调度（如 XXL-JOB）或加 `SELECT ... FOR UPDATE SKIP LOCKED` |
